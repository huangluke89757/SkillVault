# SkillVault v1.3.3 产品需求文档（PRD）

- 版本：v1.3.3
- 日期：2026-11-15
- 类型：功能新增（发现页热门排行新增「累计高下载」与「本周飙升」榜单，Issue #4）
- 关联：`releases/v1.3.3/RELEASE-CHECKLIST.md`、Issue #4、PR #5

## 一、问题（为什么要改）

「发现」页的热门排行只有单一列表，排序依据是当前热度：看不出一个 Skill 的长期装机量，也看不出最近一周谁在涨。用户想判断「这个 Skill 是不是被广泛验证过」「最近是不是突然火起来」，只能逐个点开看详情。

## 二、目标与非目标

### 目标
- G1：新增「累计高下载」榜，按 skills.sh All Time 累计安装量倒序
- G2：新增「本周飙升」榜，按最近一个完整周的安装量倒序，卡片右上角显示「上周」安装量
- G3：两个新榜单与「仅官方」筛选、分类 Tab、分页共用同一套交互；切换榜单重置到第 1 页
- G4：默认「热门」视图不增加启动请求；新榜单首次切换时才拉取，主进程 6 小时缓存

### 非目标
- 不改变上游 skills.sh 的归集口径，不引入按日数据源
- 不改动单条安装、搜索、意图匹配等既有逻辑
- 不做榜单的手动刷新入口（沿用缓存 TTL）

## 三、方案

热门排行内新增榜单切换（`RANK_TABS`）：热门（默认）/ 累计高下载 / 本周飙升。

| 层 | 实现 |
|---|---|
| 数据 | 主进程 `market-leaderboard.ts` 解析 skills.sh All Time 页内嵌 `initialSkills`（约 600 条，含每条技能 8 周安装序列）；页面结构变化时回退 All Time JSON 第一页 |
| 缓存 | SQLite `leaderboard_cache`（迁移 v6，单行，TTL 6 小时）；冷启动首次切 Tab 才请求 |
| 排序 | 渲染层 `skill-ranking.ts` 纯函数：`rankByCumulative` / `rankByWeeklySurge` / `latestWeekInstalls` |
| 展示 | 周榜卡片右上角覆盖显示「上周」安装量；安装量格式化补充 `M` 单位（如 4.2M） |
| 交互 | 切换榜单重置页码；「仅官方」与分类 Tab 对三个榜单一致生效 |

## 四、验收标准

- [ ] 三个 Tab 均可渲染；默认进入「热门」
- [ ] 累计榜首项 `find-skills` 显示 4.2M；周榜首项 `ui-taste` 显示「上周 172.5k」
- [ ] 翻页到第 2 页正常；切回「热门」恢复原列表
- [ ] 英文界面：`All-time installs` / `Weekly surge`，副标题 `Sorted by all-time installs`
- [ ] 单测通过（91 passed / 1 skipped）；`electron-vite build` 通过

## 五、风险与取舍

| 风险 | 影响 | 处置 |
|---|---|---|
| skills.sh 页面结构变化，内嵌载荷解析失败 | 中 | 回退 All Time JSON 第一页；两者都失败时显示错误与「重试」，不缓存空榜单 |
| 上游只提供按「完整周」聚合的安装量 | 低 | 「本周飙升」= 最近一个完整周；无法拆到周一至周五（需按日数据源） |
| 榜单分页需逐页请求 JSON，实测触发 429 | 低 | 只用 All Time 页面内嵌的约 600 条，不做多页抓取 |
| 文案口径 | 低 | 按 Issue #4 原文用「累计高下载」；英文保留 `All-time installs`（上游口径为安装量） |

## 六、后续（v1.4 候选）

- 接入按日数据源，支持严格的「上周周一至周五」
- 榜单缓存手动刷新入口
- 榜单卡片增加周环比变化标识
